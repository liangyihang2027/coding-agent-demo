claude-mini 阶段一最小闭环架构

阶段一的目标不是功能完备，而是跑通一个真实 Agent 的最小 ReAct 链路： 用户输入、模型思考、工具调用、结果回填、再次思考，直到模型给出最终回答。

阶段一 · Agent Loop / Tool Protocol / CLI

一张图看完整链路

入口 CLI 启动 src/cli/index.ts 加载配置、创建 runner、初始化 ConversationState 并渲染 Ink UI。
输入 用户提交任务 CodexLikeApp 记录输入，调用 runner.run(state, input, events)。
思考 LLM 流式响应 AgentLoop 把历史消息和工具 schema 发给模型，实时消费文本和工具调用分片。
行动 执行工具 权限闸门确认后，ToolRegistry 解析 JSON、zod 校验参数、执行具体工具。
闭环 结果回填 工具结果以 role: "tool" 写回会话，再交给模型继续推理或输出最终答案。

阶段一完成标准

  • LLM Client支持 OpenAI 兼容流式接口，把内部消息转换成 provider 消息。
  • Tool Calls支持流式分片拼接，用 index 聚合 name、id、arguments。
  • Tool Registry支持工具注册、JSON Schema 暴露、JSON 参数解析和 zod 校验。
  • Agent Loop支持 ReAct 循环、工具结果回填、step 上限和错误结果回传。
  • Basic Tools已有 read、write、edit、list、glob、grep、delete、run_command。
  • CLI UI支持输入、流式输出、工具状态、命令输出 chunk 和权限确认。

核心设计原则

模型只负责决策

模型输出文本或工具调用，真正的文件、命令和权限行为都落在本地工具层。

错误也进入闭环

工具失败不会直接炸掉主循环，而是作为 ToolResult 回填给模型，让模型有机会修正。

协议层保持清晰

Message、ToolCall、ToolDefinition 是模块之间的稳定契约。

一次用户请求的时序流程

CLI 初始化运行环境

执行 pnpm dev 后进入 src/cli/index.ts。 这里读取环境变量，创建 OpenAI runner 或 Cursor runner。阶段一学习主线是 OpenAI runner，也就是 OpenAIClient + ToolRegistry + AgentLoop。

创建会话状态和系统提示

ConversationState 在构造时写入 system prompt。 后续 user、assistant、tool 三类消息都会追加到同一个消息数组里，形成模型下一轮推理的上下文。

用户在 CLI 输入需求

CodexLikeApp 收到输入后，把用户消息显示到界面，并调用 runner.run(state, input, events)。这些 events 用来把模型文本、工具状态、 命令实时输出和权限确认同步回 UI。

AgentLoop 进入 ReAct 循环

AgentLoop.run 先 state.addUser(input)， 然后最多循环 maxSteps 次。每一轮都先调用模型，再根据是否有工具调用决定继续行动还是结束。

工具注册表暴露工具能力

调模型前，ToolRegistry.toLLMTools() 把每个工具的 zod 参数 schema 转成模型可理解的 JSON Schema。模型看到的不是任意本地能力，而是被注册表显式声明过的一组工具。

LLMClient 消费流式响应

OpenAIClient.stream 一边 yield 文本 delta，一边把 delta.tool_calls 交给 ToolCallAssembler。 文本 delta 直接进入 UI；工具调用要等分片拼完整后再交给 AgentLoop。

ToolCallAssembler 拼接工具调用

流式 tool_calls 的难点是一个工具调用会被拆成多个 chunk。 当前实现用 index 作为主键，持续累加 arguments， 最后输出完整的 ToolCall[]。

无工具调用则直接结束

如果模型本轮没有返回 tool_calls，说明它已经能给最终答案。 AgentLoop 会把 assistant 文本写入 state，然后返回给 UI。

有工具调用则先写入 assistant 消息

如果模型要调用工具，AgentLoop 会先用 state.addAssistant(text, toolCalls) 记录这次 assistant 决策。 这样后续 tool result 才能在协议上对应到正确的 tool call。

权限闸门判断是否允许执行

执行工具前先经过 permission gate。低风险工具可以自动放行，高风险工具会触发 UI 确认。 如果用户拒绝，拒绝原因也会作为工具结果写回 state。

ToolRegistry 运行具体工具

注册表负责解析模型给出的 JSON 字符串，用 zod 校验参数，然后调用工具的 execute(args, ctx)。工具拿到统一的 cwd 和可选 onChunk。

工具结果回填到会话

工具返回 { content, isError } 后，UI 更新工具状态， ConversationState.addToolResult 把结果追加成 role: "tool"。 这一步就是从行动回到思考的关键。

回到模型继续推理

AgentLoop 回到下一轮，把包含工具结果的新消息历史再次交给模型。 模型可以继续调工具，也可以基于结果给最终回答。达到 maxSteps 会触发安全停止。

ReAct 最小闭环图

思考层：AgentLoop + LLMClient

  • 读取 ConversationState.all() 作为模型上下文。
  • 通过 ToolRegistry.toLLMTools() 告诉模型可用工具。
  • 消费流式文本和工具调用事件。
  • 根据 tool_calls 是否为空决定结束或行动。

行动层：Permission + ToolRegistry + Tools

  • 先评估风险，必要时请求人工确认。
  • 解析 JSON 参数并做 zod 校验。
  • 调用文件、搜索、编辑或命令工具。
  • 把成功或失败结果统一封装为 ToolResult。

记忆层：ConversationState

  • system：系统提示，定义 Agent 行为边界。
  • user：用户当前需求。
  • assistant：模型文本和工具调用决策。
  • tool：工具执行结果，用 toolCallId 关联。

展示层：Ink CLI UI

  • 实时展示模型文本 delta。
  • 展示工具开始、运行中、成功或失败状态。
  • 展示命令工具的 stdout/stderr chunk。
  • 在高风险动作前显示 y/n 审批提示。
CLI

入口层要点

  • loadConfig() 决定 provider。
  • createDefaultRegistry() 注册阶段一工具。
  • loadSystemPrompt() 初始化 system message。
  • render(CodexLikeApp) 进入交互界面。
Agent

循环层要点

  • 单轮用户输入内允许多次模型和工具交替。
  • maxSteps 防止无限循环。
  • 工具失败被回填，不直接中断。
  • 最终返回最后一次 assistant 文本。
LLM

模型层要点

  • 内部消息转换为 OpenAI chat messages。
  • 文本增量立即 yield 给 UI。
  • tool_calls 分片先缓存再 finalize。
  • done 事件携带 finish reason。
Tools

工具层要点

  • 工具名字必须唯一注册。
  • 参数从 zod schema 派生 JSON Schema。
  • 运行前统一 JSON parse 和 safeParse。
  • 返回内容面向模型阅读和纠错。
Permission

权限层要点

  • 读操作低风险，写和删除风险更高。
  • 危险命令会被标记为高风险。
  • 拒绝结果也会进入模型上下文。
  • 阶段三还需要在 sandbox 层再次拦截。
State

状态层要点

  • 当前只是简单消息数组。
  • 顺序非常重要，决定模型看到的上下文。
  • tool result 必须携带 toolCallId。
  • 阶段五会接入压缩和 token 预算。

阶段一的边界和下一阶段接口

阶段一已经证明什么

  • Agent 可以接收自然语言任务，并让模型选择是否调用工具。
  • 工具调用可以通过流式协议稳定拼接出来。
  • 本地工具执行结果可以重新进入模型上下文，形成闭环。
  • CLI 可以承载流式文本、工具状态和权限确认。

阶段一刻意没有解决什么

  • diff 只有基础唯一字符串替换，尚未完成可靠 patch 引擎。
  • sandbox 只是最小可跑命令执行，安全和进程管理还很弱。
  • search 还没有自研代码检索和符号索引。
  • context 还没有 token 计量、裁剪和摘要压缩。

这份文档只描述阶段一最小闭环。后续阶段的目标不是推翻这条链路，而是把其中的工具执行、 文件编辑、代码检索和上下文管理逐步替换成更可靠、更可解释的内核实现。
